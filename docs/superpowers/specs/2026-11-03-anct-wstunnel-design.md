# ANCT-wstunnel 要件定義書

- 作成日: 2026-11-03
- 対象リポジトリ: `ANCT-wstunnel`
- ステータス: ドラフト（承認待ち）

---

## 1. 背景と目的（なぜ作るか）

旭川高専(ANCT)の学内LANは、実機(Jetson)調査により以下の制約が確認されている。

- 直接のインターネット通信は不可。ICMP、プロキシを通さないTCP 80/443はすべてブロック。
- 外部への出口は HTTPプロキシ `websec.asahikawa-nct.ac.jp:8080` のみ。PEAP認証でLANに参加する。プロキシ経由のHTTP/HTTPSは通る。**プロキシのCONNECT自体には認証不要**（Jetson実測で確認済み。よってアプリにプロキシ資格情報UIは不要）。
- プロキシはTLSの中身を検査していない（正規証明書がそのまま透過する）。
- ポート単位の遮断がある。`443` へのHTTPS CONNECT は通るが、`51820`(WireGuard)・`41641`(Tailscale) へのCONNECTは不可。
- DNSシンクホールがあり、Tailscale関連ホスト名は不正なIPに解決される。VPN/メッシュVPNは名前とポートの両方で意図的に遮断されている。

この環境では Tailscale や通常のVPNは機能しない。そこで、**遮断されていない「443番へのHTTPS CONNECT」だけを使い、WebSocketトンネル(wstunnel)で学外の自前VPSへ到達し、その上でWireGuardを通す**ことで、学内LANから自由なインターネット接続を確立する。偽装(SNI詐称など)は行わず、ブロックリストに載っていないホスト名・ポートをそのまま使う。

本プロジェクトは、この仕組みを **(A) VPS側セットアップスクリプト** と **(B) Windowsデスクトップアプリ** の2つの成果物として実装し、作成者本人だけでなく研究室の後輩でも容易に導入・利用できるようにする。

> 運用上の注意: この通信は学内アカウントに紐づく。学内ネットワーク利用規約に抵触しないか、情報システム部門への確認が望ましい（本人責任）。本設計は技術仕様のみを定義する。

---

## 2. 利用者と利用シーン

- **主利用者**: 作成者本人。学内端末(Windows)から学外へ安定して出たい。
- **副利用者**: 研究室の後輩。ネットワークの深い知識なしに、配布物を導入して使えること。
- **運用モデル**: **各ユーザーが自分専用のVPSを1台持つ**（集中管理しない。拡張性・独立性を優先）。1VPSにつき自分のクライアントが接続する。

## 3. 全体アーキテクチャ

```
[Windows端末 (学内LAN)]                                   [VPS (学外, Ubuntu)]
                                                          
 WireGuard tunnel (wintun)                                 WireGuard server
   AllowedIPs = 0.0.0.0/0                                    (loopback UDP のみ待受)
   Endpoint = 127.0.0.1:<Lport>                              ip_forward=1 + NAT(masquerade)
        │ localhost UDP                                            ▲ localhost UDP
        ▼                                                          │
 wstunnel client ──HTTPS CONNECT :443──▶  wstunnel server (:443, TLS/自己署名)
   via 学内プロキシ                            │
   (websec.asahikawa-nct.ac.jp:8080)          ▼
                                            そのままインターネットへ
```

経路の要点:
- WireGuard(UDP)を wstunnel で WebSocket(wss, 443) にくるみ、学内プロキシの HTTPS CONNECT で通す。
- WireGuardのパケットはWindows側のローカルUDPポートに入り、wstunnelクライアントがVPSへ転送。VPS側のwstunnelがloopbackのWireGuardサーバへ渡す。
- WireGuardサーバはNAT(masquerade)して通常のインターネットへ出す。
- VPS側のWireGuard UDPポートは**loopbackのみ**で待受け、外部から直接は触れない（wstunnel経由のみ）。

## 4. 成果物A: VPS側セットアップスクリプト

### 4.1 前提
- 新規に立てた **Ubuntu**(LTS想定)のVPS、クリーンな状態、root/sudo権限あり。
- グローバルIP または VPS純正のDDNS名を持つ。**独自ドメインは不要**。**接続先は VPS純正DDNS名を既定（優先）** とする（一部フィルタは生IPや未分類ホストへのCONNECTを拒否しうるため、名前解決される実在ホスト名の方が無難）。IP直指定も設定として選べるよう残す。VPS構築後に生IPとDDNS双方で443 CONNECTを実測して通る方を採るのが安全。
- 443番ポートが空いている。

### 4.2 やること（スクリプト1本で全自動を既定とする）
後輩に配るため、手順書方式ではなく **1本のシェルスクリプトを流せば完了** を既定とする。スクリプトは冪等に近い形で、以下を自動実行する。

1. 必要パッケージ導入（`wireguard-tools` 等）、`wstunnel` サーバ用バイナリの配置。
2. WireGuardサーバ鍵ペア生成、サーバ設定作成（loopback UDPで待受、クライアント1ピア登録）。
3. `net.ipv4.ip_forward=1` 有効化、送出インターフェース判定、NAT(masquerade)設定。
4. 自己署名TLS証明書の自動生成（wstunnel server用）。
5. wstunnelサーバを **:443** で起動する systemd サービス化（loopbackのWireGuard UDPへ転送）。WireGuardサーバもsystemdで常時起動。
6. **クライアント接続情報バンドルを1ファイル出力**。後輩はこのファイルをWindowsアプリに読み込ませるだけ。

### 4.3 出力する接続情報バンドル
Windowsアプリが読み込む1ファイル（形式はビルダーに委任。JSON等の機械可読形式を推奨）。最低限、次を含む:
- サーバ到達先: グローバルIP または DDNS名、ポート(443)
- 自己署名証明書の検証用情報（証明書そのもの、またはフィンガープリント）
- WireGuardクライアント設定: クライアント秘密鍵、サーバ公開鍵、クライアントアドレス(例 `10.88.0.2/32`)、AllowedIPs(`0.0.0.0/0`)、DNS、PersistentKeepalive
- wstunnelのローカル転送指定に必要な情報（ローカルUDPポート、VPS側ターゲット）
- **プロキシ到達先**（`websec.asahikawa-nct.ac.jp:8080`。クライアントが自己経路を確保するために使う。§5.4参照）
- **WireGuard MTU**（設計者判断で確定: 多重カプセル化のため小さめの固定値、例 1280。VPSスクリプトとアプリで同一値を共有するためバンドルに含める）

### 4.4 決定事項
- TLSは自己署名（独自ドメイン不要、学内プロキシはTLS非検査のため実害なし）。
- WireGuardアドレス帯は固定既定（例 `10.88.0.0/24`、サーバ `.1`/クライアント `.2`）。ビルダーが具体値を決めてよい。
- 既定ではクライアント1ピアを生成。**追加ピア発行は任意の拡張**（nice-to-have、ビルダー判断で簡易なコマンドを用意してもよい）。

## 5. 成果物B: Windowsデスクトップアプリ

### 5.1 位置づけ
Tailscaleのような、**ON/OFFと接続先設定ができる簡易なデスクトップアプリ**。難しい設定は不要で、VPSスクリプトが吐いた接続情報バンドルを読み込めば接続できる。

### 5.2 技術方針（決定事項、私の判断）
- **C#/.NET（WPF + タスクトレイ常駐）**。Windows専用。
- **ランタイム同梱の単一実行ファイル**として配布（後輩はダウンロードして起動するだけ。追加ランタイム導入不要）。
- 下回りは既存OSSバイナリを**同梱・呼び出し**（fork改造より壊れにくい）:
  - `wstunnel.exe`（配布バイナリを同梱）: WebSocketトンネルのクライアント。
  - **公式 WireGuard for Windows**: wintunドライバと `wireguard.exe` トンネルサービスを提供。アプリから同梱MSIを導入するか、前提としてインストールを促す（ビルダー判断。後輩の手間を最小化する方を選ぶ）。

### 5.3 権限・常駐モデル（決定事項）
- WireGuardトンネルの起動には管理者権限が必要。
- **インストール時だけ管理者許可 → 以降はバックグラウンドのWindowsサービスが常駐**し、日々のON/OFFはUAC無しで行える（Tailscale方式）。
- GUIは軽量フロントとしてサービスに指示を送る。実際のwstunnelプロセス起動とWireGuardトンネルの出し入れはサービス(LocalSystem)が担う。
- **コード署名（決定事項）**: 署名証明書は無い前提。自作バイナリ（アプリ本体・サービス・インストーラ）は未署名で配布し、初回起動時のSmartScreen／管理者プロンプト回避手順（「詳細情報 → 実行」等）を後輩向けドキュメントに明記する。将来、署名証明書を入手できれば署名する（任意拡張）。なおwintunドライバ自体はWireGuardにより署名済み。

### 5.4 動作フロー
- **接続ON**: サービスが (1) wstunnelクライアントを起動（学内プロキシ経由でVPS:443へwss接続、ローカルUDPを開く）、(2) WireGuardトンネルをwintunで起動（Endpoint=`127.0.0.1:<Lport>`、AllowedIPs=`0.0.0.0/0`）。
- **接続OFF**: WireGuardトンネル停止 → wstunnelクライアント停止。
- **学内プロキシ**: wstunnelクライアントがHTTPプロキシ(`websec.asahikawa-nct.ac.jp:8080`)経由でCONNECTする設定を持つ。プロキシ設定はバンドルに含めるか、アプリ側で既定値＋編集可能にする（ビルダー判断）。
- **自己署名TLS**: クライアントは証明書を検証しない設定、またはバンドルのフィンガープリントでピン留め（ピン留めが望ましい。ビルダー判断）。
- **自己経路の確保（設計者判断で確定）**: AllowedIPs=`0.0.0.0/0` かつ Endpoint がloopback(`127.0.0.1`)のため、WireGuard for Windowsの自動エンドポイント除外ルートが効かず、wstunnelがプロキシへ出ていくTCPがトンネルに吸い込まれて自己ブラックホール化する危険がある。これを防ぐため、サービスは接続ON時に**プロキシのIPへのホストルート（デフォルトルートより優先）を追加**し、wstunnel→プロキシの通信が物理LAN経路を通るようにする。切断時に該当ルートを撤去する。

### 5.5 UI（簡易）
- **タスクトレイ常駐アイコン**: 接続/切断の状態を色やアイコンで表示。右クリックでON/OFF・終了。
- **メインウィンドウ**（Tailscale風に最小限）:
  - 大きな **接続ON/OFFトグル**。
  - **現在の状態**表示（未接続／接続中／接続済み／エラー）。
  - **接続先**（サーバIP/DDNS名）の表示。
  - **「設定ファイルを読み込む」**ボタン（VPSスクリプトのバンドルを取り込む）。
  - 簡易なログ／直近のエラー表示（トラブル時に後輩が状況を伝えられる程度）。
- 凝ったプロファイル管理やマルチテナントUIは**非目標**。設定は1つの接続先で十分（将来の複数プロファイルは任意拡張）。

## 6. ゴール / 非ゴール / アンチゴール

### ゴール
- 学内LANから、443経由のwstunnel+WireGuardで学外VPSへ安定接続できる。
- VPS構築がスクリプト1本で完了し、出力バンドルをアプリに入れるだけで後輩が接続できる。
- WindowsアプリでワンクリックON/OFFでき、日常利用でUACが出ない。

### 非ゴール
- 集中管理サーバ／多人数のピア管理UI（各自が自分のVPSを持つ前提）。
- 独自ドメイン・正規証明書の取得。
- Windows以外のOS向けクライアント。
- 学内LANをまたぐ下流機器ゲートウェイ化（Jetson等でのルーター化は別件。本プロジェクトはWindowsクライアント単体）。

### アンチゴール（技術的に動いても失敗とみなす）
- 偽装（SNI詐称等）に依存する実装。ブロックリストに無いホスト名・ポートをそのまま使う方針を崩さない。
- 後輩が導入時に手動でコマンドを何段も打たないと動かない状態。
- 認証情報や秘密鍵を平文でリポジトリ・ログに残す実装。

---

## 7. 制約

- 学内プロキシ `websec.asahikawa-nct.ac.jp:8080` 経由のHTTPS CONNECT(443)のみが外部到達手段。
- TLSは自己署名（独自ドメインなし）。
- Windows側はwintunドライバ利用のため管理者権限が一度は必要。
- VPSはUbuntu/クリーン状態・443空き・グローバルIPまたはDDNSを前提。

---

## 8. ビルダーに委ねる範囲

- 各ツールの正確なバージョン、wstunnel v11系の具体的なコマンド構文とフラグ。
- バンドルファイルの具体フォーマット（JSON等）とフィールド名。
- WireGuardアドレス帯・ポート番号の具体値。
- 公式WireGuard for Windowsを「同梱MSIで自動導入」か「前提として案内」かの選択（後輩の手間最小を基準に）。
- 自己署名証明書を「検証なし」か「フィンガープリントでピン留め」か（ピン留め推奨）。
- Windowsサービスとの通信方式（名前付きパイプ等）、インストーラの作り（単一exe配布＋サービス登録）。
- 追加ピア発行・複数プロファイルなどの任意拡張の有無。
- テスト・CIの構成。
